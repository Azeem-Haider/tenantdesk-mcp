Application Security Assessment

TenantDesk v0.1.0

Multi-tenant SaaS: REST API, MCP server and Stripe webhook

Prepared by Azeem Haider, Backend Integration Engineer
Assessment date: 14 October 2026 · Report version 1.0

Sample report. TenantDesk is a demo application built for this portfolio, and the issues in v0.1.0 were introduced on purpose to show the assessment process end to end. No client systems or real customer data were involved. Code and reproduction scripts: github.com/Azeem-Haider/tenantdesk-mcp (tag v0.1.0 for the assessed build, main for the fixed build).

1. Executive summary

TenantDesk lets several clinics share one platform, with an AI assistant (via MCP) that reads and acts on their data. The assessment asked one question first: can one clinic, or an AI acting for it, reach another clinic's data or money?

In v0.1.0 the answer was yes, in three separate ways: a changed parameter in the customer export, an invoice lookup without a tenant check, and an AI tool that accepted a tenant id from the model. The Stripe webhook also accepted forged payment events from anyone on the internet, and the AI refund tool let any staff member refund any amount in a single call.

2. Scope and rules of engagement

TargetTenantDesk v0.1.0 (git tag v0.1.0), run locally with seeded demo data
In scopeREST API (/api/customers/export, /api/invoices/:id); MCP server over Streamable HTTP and stdio (7 tools); Stripe webhook (/webhooks/stripe); authentication and authorization; data layer
Out of scopeInfrastructure, hosting and network; denial-of-service; third-party services (Stripe itself, the AI model provider); social engineering
Test accountsTwo tenants (Acme Dental, Brightside Clinic) with admin, agent and viewer users
ApproachGrey box: source code available, plus authenticated testing as each role
DataSynthetic only. No production systems were touched.

3. Method

  • Threat model first: for each entry point, who can call it, what identity it trusts, and what it can change.
  • Checklists: OWASP API Security Top 10 (2023), OWASP Top 10 (2021) and selected OWASP ASVS 4.0 Level 2 controls for access control, authentication, error handling and logging.
  • AI/MCP-specific: tool arguments treated as attacker-controlled (prompt injection), privilege of AI actions, human confirmation for money-moving tools, auditability.
  • Payments: webhook authenticity, replay windows, duplicate delivery and idempotency.
  • Evidence: every finding is backed by a scripted proof of concept (assessment/poc.ts) so it can be reproduced and retested exactly.

Severity: CVSS v3.1 base score, with business impact noted where it differs (for example TD-06, which moves money).

5. Detailed findings

TD-01

Cross-tenant customer export via tenant_id parameter

SeverityHigh  CVSS 7.7
VectorCVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:N/A:N
ComponentREST API · src/api.ts, src/repo.ts (listCustomers)
StatusFixed in v0.2.0, verified on retest

Description

The customer export endpoint accepts an optional tenant_id query parameter and passes it to the data layer, which uses it instead of the caller's own tenant. Any signed-in user can download the full customer list (names, emails, plans) of any other clinic by changing one parameter.

Steps to reproduce

GET /api/customers/export?tenant_id=t_bright
Authorization: Bearer <token for u_ben, Acme Dental agent>

Evidence

HTTP 200, CSV contains Brightside Clinic customers (e.g. "Sam Okafor").

Impact

Full cross-tenant disclosure of customer personal data. This is the most serious class of bug in a multi-tenant SaaS: one customer can read another customer's data, which is reportable under GDPR and usually ends contracts.

Recommendation

Never accept a tenant identifier from the request. Derive the tenant from the authenticated session only, and enforce it in the shared data layer so no endpoint can override it. Add Postgres row-level security as a second barrier.

Retest

v0.2.0: the parameter is ignored; TenantScope always filters by the session tenant. Retest returned only Acme data.

TD-02

Insecure direct object reference on GET /api/invoices/:id

SeverityMedium  CVSS 5.0
VectorCVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:L/I:N/A:N
ComponentREST API · src/repo.ts (getInvoice)
StatusFixed in v0.2.0, verified on retest

Description

The invoice lookup queries by invoice id only, without a tenant filter. A user who knows or guesses another tenant's invoice id can read its amount, status and customer reference.

Steps to reproduce

GET /api/invoices/inv_b1
Authorization: Bearer <token for u_ben, Acme Dental agent>

Evidence

HTTP 200 with Brightside Clinic invoice inv_b1.

Impact

Cross-tenant disclosure of billing data. Invoice ids are short and sequential-looking, so enumeration is practical.

Recommendation

Scope every lookup by tenant (where tenant_id = $session_tenant and id = $id) and return the same 404 for "belongs to someone else" and "does not exist".

Retest

v0.2.0: lookup is tenant-scoped; retest returned 404.

TD-03

MCP tool accepts tenant_id from the model (prompt-injection data access)

SeverityHigh  CVSS 7.7
VectorCVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:N/A:N
ComponentMCP server · src/server.ts (list_customers)
StatusFixed in v0.2.0, verified on retest

Description

The list_customers tool exposes a tenant_id argument. The AI model fills tool arguments, so any text the model reads (a support ticket, an email, a document) can instruct it to pass another tenant's id. The server trusts the argument.

Steps to reproduce

tools/call list_customers {"tenant_id": "t_bright"}
(as u_ben, Acme Dental agent, over the MCP HTTP endpoint)

Evidence

Tool returned Brightside Clinic customers.

Impact

Same data exposure as TD-01, but reachable through prompt injection: an attacker never needs credentials, only a way to get text in front of the model.

Recommendation

MCP tools must not take tenant, user or role identifiers. Resolve the principal from the transport (verified token) and apply it server-side. Treat every tool argument as attacker-controlled.

Retest

v0.2.0: no tool accepts a tenant id; extra arguments are dropped. Retest returned only Acme data.

TD-04

Stripe webhook accepted without signature verification

SeverityHigh  CVSS 7.5
VectorCVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N
ComponentWebhook · src/api.ts (handleStripeWebhook)
StatusFixed in v0.2.0, verified on retest

Description

The /webhooks/stripe endpoint parses and acts on any JSON body. It does not check the Stripe-Signature header, so anyone on the internet can send fake payment events.

Steps to reproduce

POST /webhooks/stripe
{"id":"evt_forged_1","type":"invoice.paid","data":{"object":{"metadata":{"invoice_id":"inv_a2"}}}}
(no signature header, no authentication)

Evidence

HTTP 200; open invoice inv_a2 changed to "paid".

Impact

Unauthenticated attackers can mark invoices as paid (getting service without paying) or trigger any other webhook-driven state change.

Recommendation

Verify the HMAC-SHA256 signature over the raw body with the endpoint secret, compare in constant time, and reject events outside a 5-minute timestamp window.

Retest

v0.2.0: signature and timestamp verified; retest got HTTP 400 and the invoice stayed open.

TD-05

Webhook events not de-duplicated; refunds double-counted on retry

SeverityMedium  CVSS 5.3
VectorCVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N
ComponentWebhook · src/api.ts
StatusFixed in v0.2.0, verified on retest

Description

Stripe delivers events at least once and retries on timeouts. The handler processes every delivery and adds the refunded amount each time instead of storing Stripe's running total.

Steps to reproduce

Deliver the same signed charge.refunded event (amount_refunded: 2000) three times.

Evidence

Invoice refunded_cents became 6000 instead of 2000.

Impact

Financial records drift from Stripe; refunds and revenue reports are wrong. Happens on its own during normal Stripe retries, and on purpose when combined with TD-04.

Recommendation

Record each event id in a processed-events table and skip duplicates. Write absolute values from the event (Stripe's totals), never increments.

Retest

v0.2.0: events de-duplicated by id; refund total is set, not added. Retest: refunded_cents = 2000.

TD-06

Refund tool missing role check, amount cap and human confirmation

SeverityMedium  CVSS 6.5
VectorCVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N
ComponentMCP server · src/server.ts, src/repo.ts (issue_refund)
StatusFixed in v0.2.0, verified on retest

Description

The issue_refund tool refunds immediately in one call, for any amount, for any signed-in role. The model can trigger it on its own, including after a prompt injection.

Steps to reproduce

tools/call issue_refund {"invoice_id":"inv_a1","amount_cents":12000,"reason":"..."}
(as u_ben, an agent, not an admin)

Evidence

Full $120.00 refunded by an agent with no confirmation step.

Impact

Direct money loss. Business impact is higher than the CVSS score suggests, because one manipulated conversation can issue refunds.

Recommendation

Split money-moving actions into request and confirm steps, restrict to admins, cap the amount the AI may start, bind the confirmation to the same user and a short expiry, and mark the tool as destructive so MCP clients ask the human.

Retest

v0.2.0: request_refund + confirm_refund, admin only, $500 cap, same-admin, 10-minute expiry, single use. Retest: agent denied, nothing refunded.

TD-07

Role and tenant taken from token claims; downgraded users keep old rights

SeverityMedium  CVSS 4.2
VectorCVSS:3.1/AV:N/AC:H/PR:L/UI:N/S:U/C:L/I:L/A:N
ComponentAuth · src/auth.ts (principalFromToken)
StatusFixed in v0.2.0, verified on retest

Description

If a token carries tenant_id and role claims, they are trusted without checking the database. A user who is downgraded or removed keeps their old role until the token expires (8 hours).

Steps to reproduce

Use a valid token minted with role=admin for u_cara, whose current role is viewer, and call create_ticket.

Evidence

Ticket created by a user who is a viewer in the database.

Impact

Revocation doesn't take effect; a fired employee or downgraded user keeps access for hours.

Recommendation

Put only the user id in the token and load tenant and role from the database on each request (or keep tokens very short-lived with a revocation list).

Retest

v0.2.0: claims ignored; role and tenant loaded per call. Retest: denied.

TD-08

Database error details exposed to the MCP client

SeverityMedium  CVSS 4.3
VectorCVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:N/A:N
ComponentMCP server · src/server.ts (error handling)
StatusFixed in v0.2.0, verified on retest

Description

Unexpected errors are returned to the client verbatim, including raw Postgres messages.

Steps to reproduce

tools/call search_invoices {"from":"2026-13-45"}

Evidence

Response: date/time field value out of range: "2026-13-45"

Impact

Reveals the database engine and query structure, which helps an attacker craft further attacks; also puts internal details into AI conversation logs.

Recommendation

Return generic messages for unexpected errors, log the detail server-side with a correlation id, and validate inputs strictly before they reach the database.

Retest

v0.2.0: unexpected errors return "internal error". Retest confirmed.

TD-09

CSV export allows spreadsheet formula injection

SeverityMedium  CVSS 5.4
VectorCVSS:3.1/AV:N/AC:L/PR:L/UI:R/S:C/C:L/I:L/A:N
ComponentREST API · src/api.ts (csvCell)
StatusFixed in v0.2.0, verified on retest

Description

Customer fields are written to CSV unchanged. A value starting with =, +, - or @ becomes a live formula when staff open the export in Excel or Google Sheets.

Steps to reproduce

Set a customer name to =HYPERLINK("http://evil.test","Click") and export as an admin.

Evidence

Exported cell contains the live formula.

Impact

Phishing links or data-exfiltration formulas run in staff spreadsheets.

Recommendation

Prefix cells that start with formula characters with a single quote and quote-escape every cell.

Retest

v0.2.0: formula characters neutralised. Retest: exported as text.

TD-10

No audit trail of actions taken through MCP tools

SeverityInformational  CVSS n/a
VectorNot scored
ComponentMCP server · src/repo.ts (audit)
StatusFixed in v0.2.0, verified on retest

Description

Tool calls made by the AI, including refunds and data reads, are not recorded.

Steps to reproduce

Run the checks above and inspect audit_log.

Evidence

0 rows after 9 tool and API actions.

Impact

No way to investigate what the AI did, who asked it, or whether data was accessed after an incident.

Recommendation

Log every tool call with tenant, user, tool, arguments and outcome, including denied calls, and alert on spikes of denials.

Retest

v0.2.0: every call logged, allowed or denied.

7. Recommendations beyond the fixes

  • Defence in depth for tenancy: add Postgres row-level security keyed on a per-request tenant setting, so a missed filter in code is still blocked by the database.
  • Cross-tenant tests in CI: keep a test per endpoint and per MCP tool that tries another tenant's ids. They are cheap and catch regressions immediately.
  • MCP tool design rules: no identity arguments, read and write tools separated, destructive tools marked and confirmed by a human, inputs validated by schema.
  • Webhook checklist: verify signature on the raw body, enforce a timestamp window, de-duplicate by event id, write absolute values, respond fast and process asynchronously.
  • Monitoring: alert on spikes of denied tool calls and cross-tenant 404s; both are early signs of probing or prompt injection.
  • Identity: move from shared-secret JWTs to the company identity provider (OAuth 2.1 / OIDC) before production.
